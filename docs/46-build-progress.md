### Persistence and policy behavior

New file in this earlier wave: `supabase/migrations/20261117030202_reviewed_business_authority.sql`. The active wave above advances the expected schema again; both migrations require actual database verification.

- Reuses `agent_team_settings` with `authority_revision` and `channel_authority`; adds service-role-only `business_context_reviews` and `business_owner_commands`, with RLS enabled and browser grants revoked. RPCs use security invoker and explicit scoped keys.
- Commands lock the business, check revisions, atomically save history/result and apply supported changes. Replaying the same actor/key/command returns its existing receipt; changed commands cannot reuse that key.
- Review compares profile timestamps as timestamps, stores the displayed source revision and refuses conflicting assistant knowledge. Profile/knowledge edits invalidate reviews and authority revisions. Runtime authority also caps unreviewed/conflicting context to observation.
- Legacy settings/activation writes bump authority revisions. New unreviewed activation starts observing. An explicit stopped channel remains stopped across activation saves. Connecting an account does not override provider read-only grants.
- Approval authority is pinned at proposal preparation, never silently renewed by Approve. Existing eligible unsent proposals/jobs are backfilled inside one atomic DO statement that disables/restores only the existing immutable-approval and enqueue triggers. Accepted, processing, provider-pending and uncertain records are excluded, as are legacy failed CRM or failed rows with an external reference.
- Stops cancel eligible unsent actions and related assignments while leaving inbound collection and provider reconciliation intact. SQL conversation queues return null when suppressed rather than throwing away the inbound message. Booking children inherit one validated revision; startup and final effect checks reject stale work.
- Queue policy reads intentionally do not lock settings while holding conversation/work rows. A concurrent stop can leave a stale queued row; pinned revisions and final checks suppress its effect. Prove concurrency and lock behavior in Postgres before acceptance. No local policy flag can recall a request already accepted by a provider.
